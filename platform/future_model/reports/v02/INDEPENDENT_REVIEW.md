# Independent review of Psychohistory Platform v0.2

I reviewed the implementation against `docs/V02_PLAN.md` and `docs/V02_WORKFLOW.md`, from base `7ea6eab94433e3669b6f492d802bb35316dc90d6` through the working changes and the subsequent release candidate `3f69a6bfd5fe0d9021f0e514bcf7a4b1c3126e4d`. Paths below are relative to `platform/future_model`. The review covered the source manifests, evidence capture, mathematical plugin, synthetic benchmark, SQLite persistence, scheduler, worker, API, CLI, Chinese Web UI, verification scripts and changed tests. Probes used temporary data and local Git objects.

## Findings and disposition

1. **High, corrected. Holdout reuse after scoring.** In the initial `src/psychohistory/runtime.py` implementation, every unsuccessful terminal state could be retried under the same holdout, and retries could bind new code. I injected an ordinary storage failure after the worker returned valid metrics. The first run became `FAILED`, then a replacement run scored that same holdout and became `COMPLETED`. The release candidate binds executable code to the protocol and reserves the holdout durably before launching the worker. A consumed holdout stays closed across failure and restart. Pre-dispatch cancellation or compatibility rejection can still lead to a separate auditable retry. See `runtime.py` around lines 76 and 181, and `workflow.py` around lines 54 and 83.
2. **Important, corrected. Legacy API and CLI accepted v2 experiment identifiers.** I observed HTTP 200 with `kind=prediction-comparison-v1` at the v1 detail endpoint. Legacy lifecycle and result operations used that same unfiltered lookup. The release candidate filters single-run operations and lists by kind. The API test checks v1 detail, result, approve and cancel all return 404 for v2 IDs.
3. **Important, partially corrected at this revision. Incomplete results could be published.** The initial version accepted a four-field identity receipt without any scores or scientific scope. `src/psychohistory/v02_execution.py` now checks the top-level scope, identities, bounded scores, selection, and branch hashes on publication and on historical reads. At lines 122–131 the nested collections can still contain incomplete studies and only two sensitivity scenarios. My probe retained only `metrics` and `evidence` per study and removed the third scenario. `validate_result` accepted the modified report. `web/src/ResearchWorkflow.tsx` around lines 160–169 then dereferences missing study window, baseline, or weights. Check exact frozen study identities, three scenarios and normalized weights, and the fields required by the viewer before accepting the report. Add a negative test for a partially missing study and an absent sensitivity scenario.
4. **Important integrity check. Bind the lookup key to the source payload.** `src/psychohistory/workflow.py` around lines 38–46 validates the contents of a stored source but does not compare its `source_id` with the requested key. If an internally valid MAIN payload is associated with another key in storage, its content checks pass and the caller can persist that unrelated key in a protocol. The public registration flow produces matching keys. This exposure concerns incorrect or mismapped restored metadata. Add the same lookup-key check already used for protocol records, and test a mismatched source row.
